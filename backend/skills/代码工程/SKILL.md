# 代码工程

接到写代码任务时，按**专业开发纪律**执行。核心原则：**写出来不是目的，写出来能跑才是。**

## 铁律（违反任何一条 = 交付不合格）

1. **不编造**：不确定的 API、库、函数签名，先用 `web_search`/`web_fetch` 查证，或先用 `shell_exec` 试一下再写。**绝不凭印象写可能不存在的接口。**
2. **写后必验**：任何代码文件写完后，**必须**调 `code_check` 做语法校验；能运行的**必须真跑一次**（`shell_exec`），看实际输出。
3. **验证要说实话**：交付时明确区分「已实测通过」和「未运行/仅语法检查」。**没跑过就说没跑过，绝不假装验证过。**
4. **改前先读**：修改已有代码前，先 `file_read` 看清现有实现和风格，**按项目现有风格写**（命名、缩进、注释密度、错误处理方式）。

## 工作流

1. `update_plan`：需求拆解 → 实现 → 验证 → 交付（四步计划）
2. **调研**：涉及不熟悉的库/版本时先查文档（web_search），确认接口存在
3. **实现**：`file_write` 写入（大文件分段写，每段写完可 code_check 增量验证）
4. **验证**（逐级升级，至少做到第 2 级）：
   - L1 语法：`code_check path`（Python/JS/JSON/HTML 均支持）
   - L2 运行：`shell_exec` 真跑（`python xxx.py`）——**必做**
   - L3 测试：有测试就跑测试；没测试就写个最小验证脚本跑
5. **自查清单**（交付前逐条过）：
   - [ ] 所有 import 的库都确认存在（或已安装）
   - [ ] code_check 通过
   - [ ] 真跑过，输出符合预期（贴出实际输出）
   - [ ] 没有 `TODO`/`pass`/`NotImplementedError` 占位（除非任务本来就是搭骨架）
   - [ ] 没有硬编码的密钥/绝对路径（密钥走环境变量）
   - [ ] 错误处理存在（不是 happy path only）
6. **交付**：`task_done` 说明——实现了什么、如何验证的（贴命令与真实输出）、已知限制

## 反模式（看到自己写这些就停下重做）

- ❌ 用了 `import foo` 但从未确认 foo 存在
- ❌ 调用了 `lib.some_function(...)` 但不确定签名——凭印象猜参数
- ❌ 写了代码直接 task_done，没有 code_check、没有运行
- ❌ 交付语写"已测试通过"但实际只做了语法检查
- ❌ 在代码里留 `# TODO: 在这里处理错误`
- ❌ 把用户的 API Key 硬编码进代码（必须走环境变量）

## 语言注意事项

- **Python**：`py_compile` 能查语法但不查类型；运行前确认依赖已装（`pip show xxx` 或直接跑）
- **JavaScript/Node**：`node --check` 查语法；运行注意 ESM/CJS 差异（`.mjs` vs `.cjs`）
- **HTML/前端**：标签平衡只靠 code_check 粗检——**真正的验证是浏览器打开看**（用 browser_navigate 打开检查渲染）
- **Shell 脚本**：写完用 bash -n 检查（`shell_exec: bash -n script.sh`）
